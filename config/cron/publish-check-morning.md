# 发布状态晨间补检

- **调度**：`42 8 * * *`（Asia/Shanghai，触发后先随机抖动 0~20 分钟再执行）
- **作用域**：仓库根目录
- **产物**：`metrics/raw/<今天日期>.json` 各平台 `publishedList`，随后 `npm run gen:data`

## 为什么要有这一轮

`daily-collect.md` 那轮在 21:47 跑，而发文时间固定在 22:00 前后——当晚发出去的内容
要等到第二天 21:47 才被认出，发布日历上一整天挂着「到期未发」，是假账。
这一轮只做「已发布列表」回认，不重复采指标。

## 指令（逐字，重建任务时整段复制）

> 每天早上补跑一次「已发布列表」回认，把前一晚 21:47 之后发出去的内容判成已发布——发布日历不能等到第二天晚上才认账。
>
> 背景：前一晚 21:47 已有一个「平台数据每日采集」任务跑过 publish-check，但固定发文时间在 22:00 左右，那一批永远滞后约 24 小时才被认出。这个任务只补这一件事，不重复采指标。
>
> 步骤：
> 1. 先随机等待 0~20 分钟再开始（抖动，避免每天精确同一时刻访问后台的机器特征）。可用 `sleep <随机秒数>` 实现。
> 2. 在项目根目录运行 `npm run publish-check`（经 ego-browser 用已登录的浏览器，逐平台创作者后台采「已发布内容列表」：标题+发布时间+链接，合并写入 metrics/raw/<今天日期>.json 的 platforms[key].publishedList，只改这一个字段不动别的；退出码 2 = 至少一个平台本轮失败）。全程只读列表页，绝不点任何发布/编辑控件。
> 3. 跑完必须运行 `npm run gen:data` 刷新前端数据，并核对输出里「N 篇排期文章」的计数正常（gen:data 挂了界面就是空数据，脚本自报成功不算数）。
> 4. 成败判据以产物为准：读 `metrics/raw/<今天日期>.json`，确认各平台 `publishedList` 有条目、`errors` 是否为空。
> 5. 若 `errors` 非空或某平台 publishedList 缺失——【铁律】绝不尝试破解验证码或自动登录，也不改脚本绕过风控，只明确报告「哪个平台本轮没采到、原因是什么（errors 内容）、是否需要在 ego lite 浏览器里重新登录创作者后台」。视频号登录态最容易过期，失效属预期，报告即可。
> 6. 成功时简要报告：各平台 publishedList 采到几条、以及相比昨晚有没有新回认出哪几篇（发布日历上从「未发」变「已发布」的）。
>
> 约束：只读采集，不做任何发布动作；不修改 collect / publish-check / build-data 脚本逻辑；不动 content/ 下的稿件。
