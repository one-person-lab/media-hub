- **作用域**：仓库根目录
- **产物**：`content/Resources/对标账号/<平台key>/<昵称>.md`，随后 `npm run gen:data`

## 指令（逐字，重建任务时整段复制）

> 每天自动采集同赛道的对标账号（活跃 + 粉丝多 + 有爆款），小红书与抖音各新建最多 5 份账号档案。
>
> 步骤：
> 1. 先随机等待 0~25 分钟再开始（抖动，避免每天精确同一时刻搜同一批关键词的机器特征）。可用 `sleep <随机秒数>` 实现。
> 2. 在项目根目录运行 `npm run benchmark`（整个流程 8~15 分钟属正常，不要中途判定失败）。脚本读 `config/benchmarks.json`，按 platforms 逐平台跑。两平台走同一条找法：按定位关键词搜「作品」→ 把命中的作者聚成候选池（抖音的作品卡不挂作者信息，脚本从 React fiber 里取 authorInfo.secUid 与 stats.diggCount）→ 按命中作品的最高赞排候选顺序 → 逐个访问主页取实测读数（粉丝、获赞、作品列表、简介；抖音作品发布日期由 aweme_id 雪花号反推，抖音主页简介要先点一次「更多」才拿得到完整版）→ 按 粉丝量×近期爆款×活跃度 打分 → 过门槛的新账号建档到 `content/Resources/对标账号/<平台key>/<昵称>.md`，frontmatter 含 `platform`（取 xiaohongshu / douyin，与 PLATFORM_META 同一套 key）、`desc`（账号简介原文）、`accountId`。已建档的按「平台+userId」自动跳过。
>    注意：抖音不再用搜索页的「用户」tab 找人——那个 tab 按语义匹配关键词，捞进来的是助农卖货、手势舞主播这类跑题大号；也不要改回按卡片粉丝数预筛或重排候选。
> 3. 跑完运行 `npm run gen:data` 刷新工作台数据，输出里应看到「N 个对标账号」的计数变化（这一步不能省：gen:data 挂了界面就是空数据，脚本自己报成功不算数）。
> 4. 检查输出（日志前缀是 `[bench:小红书]` / `[bench:抖音]`，逐平台各有一段）：
>    - 若报「没读到粉丝数」「没读到作品列表」「主页没加载出读数」「搜索结果始终没出现」或「连续两个主页取不到数据，停止访问该平台剩余候选」，或某平台搜索阶段全部关键词 0 命中 —— 【铁律】绝不尝试破解验证码、不自动登录、不改脚本绕过风控、不加重试，只报告「需要在 ego lite 浏览器里重新登录小红书/抖音」，并说清是哪个平台。
>    - 若只有部分关键词报「搜索结果始终没出现」（例如前四个关键词正常、后两个失败），那是短时间搜索次数偏多被限流，属可接受结果：照常处理已采到的候选，在报告里说清哪几个关键词本轮没跑成，不要重跑、不要放宽门槛。
>    - 若某平台报「今天没有新账号过门槛」，这是正常结果（候选多已建档或粉丝/活跃不达标）。不要为了凑够每平台 5 个去放宽 `config/benchmarks.json` 的门槛、不要重试、不要改关键词——门槛口径归用户拍板。
> 5. 成功时简要报告：各平台新建档几个、各自粉丝量与最高赞、以及被门槛挡掉的代表账号与原因。
>
> 约束：只读浏览搜索结果页与公开主页，不做任何关注/点赞/发布动作；不改 `config/benchmarks.json` 的关键词与门槛；不修改 `content/Resources/对标账号/` 下已有档案的 position/why/desc 字段（那是人工判断）；不动 `content/Inbox/`（那是内容两条线的数据）。
